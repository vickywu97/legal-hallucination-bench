## 1. 产品定位

### 1.1 一句话定位
**「中国法·已核验」是为 AI 应用和开发者提供的、每一条条文都经过执业律师比对官方来源并具名签署的、带版本轴的、模块化的中国法律知识库。**

### 1.2 核心价值主张

| 价值点 | 说明 | 与竞品差异 |
|--------|------|------------|
| **已核验** | 每一条条文由执业律师逐条比对官方来源，具名签署 | 竞品（北大法宝/威科）是"数据库"，不承诺"已核验" |
| **带版本轴** | 记录每一条的生效/废止日期、修订链、新旧条文号对照 | 竞品多数只有"现行版"，缺少历史版本对照 |
| **模块化** | 按法律分类，独立下载，不绑定全量 | 竞品通常只有"全量订阅"，无按需选择 |
| **可复现** | 提供核验台账 + 构建脚本，任何用户可独立验证真伪 | 竞品数据来源不透明，无法独立验证 |
| **AI 原生** | JSONL 格式、无依赖、可直接接入 RAG / Embedding 管线 | 竞品多为网页/PDF，不适合 AI 应用直接消费 |

### 1.3 核心叙事
> **"我们首先证明了 AI 在法律场景不可信——5 个国产大模型法条引注幻觉率 50%-64.6%。然后我们给出了解决方案：一个每一条都经律师核验、AI 可以直接用的可信法条知识库。"**

这条叙事贯穿产品和 Bench 两个项目，形成完整的"发现问题 → 给出方案"故事线。

## 2. 市场分析

### 2.1 市场背景
- 2024-2026 年，法律 AI 产品爆发：幂律智能、华宇元典、秘塔 AI、通义法睿、北大法宝 AI 等均已推出或正在研发法律大模型产品。
- 所有法律 AI 产品面临同一个致命问题：**模型会编造法条**。这一问题的严重性已被本项目 Bench 实测数据所证实（5 模型 HVI 50%-64.6%，增值税法域 42 次引注 0 次正确，全部 8 法域逐字 EXACT 均为 0%）。
- 解决"编造法条"问题的主流技术方案是 **RAG（检索增强生成）**——让模型在回答前先检索权威知识库，再基于检索结果生成回答。RAG 的效果**完全取决于知识库的质量**。

### 2.2 市场机会
- RAG 知识库提供商是一个新兴市场。目前市面上**没有**一个公开可用的、经过专家逐条核验的中国法律知识库。
- 北大法宝、威科先行等传统数据库虽然数据权威，但存在以下问题：
  - 价格昂贵（年费 ¥5,000-¥50,000），不适合中小团队和独立开发者
  - 不提供机器可读的批量下载格式（多为网页/PDF）
  - 不提供核验溯源信息（用户无法独立验证数据准确性）
  - 不包含版本轴信息（无法判断某条文在特定时间是否有效）
- 市场空白：**一个价格合理、机器可读、已核验、带版本轴的中国法律知识库。**

### 2.3 市场规模估算

| 目标用户类型 | 估算数量（中国） | 付费意愿 | 潜在年收入 |
|--------------|------------------|----------|------------|
| 法律 AI 初创公司 | 20-50 家 | 高（年费 ¥2万-¥10万） | ¥40万-¥500万 |
| 大型律所 | 100-200 家 | 中（年费 ¥5千-¥2万） | ¥50万-¥400万 |
| 企业法务部门 | 500-1000 家 | 中低（年费 ¥2千-¥1万） | ¥100万-¥1000万 |
| 独立开发者/学术研究者 | 1000-5000 人 | 低（免费层转化付费） | ¥10万-¥50万 |
| **合计** | — | — | **¥200万-¥1950万/年**（乐观估计） |

> **注意**：以上为市场天花板估算，不是第一年收入预期。实际收入取决于产品成熟度、品牌认知、销售能力等因素。

### 2.4 竞品分析

| 竞品 | 优势 | 劣势 |
|------|------|------|
| 北大法宝 | 数据全、品牌强 | 价格高、无核验溯源、无版本轴、无机器可读格式 |
| 威科先行 | 国际品牌、多法域 | 价格极高、无核验溯源、无版本轴 |
| 国家法律法规数据库 (flk.npc.gov.cn) | 免费、官方 | 无结构化数据、无版本轴、仅网页版、法律修订后旧版无法查看 |
| 开源法律数据集（如 Law-GPT 等） | 免费 | **未核验**（多数为 AI 自动抓取，内容准确度未知）、无版本轴、无专家背书 |
| **本产品** | **已核验、带版本轴、模块化、可复现、AI 原生格式** | 初期数据规模较小、品牌建设从零开始 |

## 3. 目标用户

### 3.1 用户画像

| 用户类型 | 典型场景 | 核心需求 |
|----------|----------|----------|
| **法律 AI 开发者** | 构建法律 RAG 应用，需要可信的知识库作为检索底座 | 机器可读格式、已核验、可批量下载 |

| **独立开发者** | 开发垂直法律 AI 应用（如劳动法咨询、税法计算器等） | 价格合理、模块化、易于集成 |

### 3.2 用户分层

| 层级 | 用户类型 | 付费意愿 | 运营策略 |
|------|----------|----------|----------|
| **核心用户** | 法律 AI 初创公司、企业法务部门 | 高 | 直接销售、产品演示、试用期 |
| **成长用户** | 大型律所、法学研究机构 | 中 | 学术合作、论文引用、社区推广 |
| **基础用户** | 独立开发者、学生 | 低 | 免费模块吸引、培养使用习惯后向付费层转化 |

### 4.2 模块设计原则
1. **独立性**：每个模块是一个独立的法律或法律组合，可单独下载和使用，互不依赖。
2. **完整性**：每个模块包含该法律的**全部条文**（不是选编、不是节选），覆盖该法律的每一版本。
3. **一致性**：所有模块使用统一的数据格式（JSONL）、字段 schema、核验标准和版本号规范。
4. **可追溯性**：每条条文附带核验台账（谁、何时、依据何种官方来源核验），构建脚本开源，任何用户可独立验证。
5. **版本化**：每个模块独立版本号，法律修订后单独更新该模块，不影响其他模块。

## 6. 数据规格

### 6.1 法条数据文件（`statutes_{模块编号}.jsonl`）

每行一个法条版本节点的 JSON 对象，字段 schema 与现有项目一致：

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `id` | string | 是 | 全局唯一标识符，格式：`{law_code}_{sort_key}_v{version}` |
| `law_code` | string | 是 | 法律助记码，如 `CIVIL_CODE`, `COMPANY_LAW` |
| `article_number` | string | 是 | 人类可读的条文号，如"第五百八十四条"、"第15条" |
| `article_sort_key` | int | 是 | 排序键，方便按条号范围查询 |
| `content` | string | 是 | 条文完整原文，用于逐字比对 |
| `effective_date` | string | 是 | 施行日期，格式 `YYYY-MM-DD` |
| `revision_of` | string/null | 否 | 若本条是某条的修订版本，指向旧版本 ID |
| `source_url` | string | 否 | 官方来源 URL，用于核对 |
| `source_accessed_at` | string | 否 | 快照日期，格式 `YYYY-MM-DD` |
| `notes` | string | 否 | 备注，如"对应旧法第 X 条" |
| `verification_status` | string | 是 | `verified` / `unverified` |

### 6.2 核验台账文件（`verifications_{模块编号}.json`）

每个节点一条核验记录，以 `{节点 id}` 为键：

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `status` | string | 是 | `verified` / `rejected` / `unverified` |
| `verified_by` | string | 是 | 核验人签名，如"Vicky Wu (律师/税务师/专利代理师)" |
| `source` | string | 否 | 核验所依据的官方来源 |
| `verified_at` | string | 否 | 核验日期，格式 `YYYY-MM-DD` |
| `notes` | string | 否 | 核验备注 |

### 6.3 模块说明文件（`README_{模块编号}.md`）

每个模块附带以下文档：

| 章节 | 内容 |
|------|------|
| 法律简介 | 该法律的名称、颁布机关、现行版本、生效日期 |
| 条文统计 | 该模块包含的总条文数、版本数、核验覆盖率 |
| 版本轴说明 | 若有多个版本，说明各版本的施行日期与对照关系 |
| 数据格式说明 | JSONL 字段 schema、加载示例代码 |
| 核验说明 | 核验方法、核验人、所依据的官方来源 |
| 已知局限 | 款/项粒度未覆盖、仅收录到"条"级别等 |
| 更新记录 | 该模块的版本号与变更日志 |

### 6.4 知识库索引文件（`knowledge_base/laws/laws_index.json`）

记录所有已收录法律的法律级元数据：

| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | string | 法律全称 |
| `aliases` | array | 常用简称列表 |
| `type` | string | `法律` / `行政法规` / `司法解释` 等 |
| `status` | string | `effective` / `repealed` |
| `effective_date` | string | 现行版本施行日期 |
| `source_url` | string | 官方来源 URL |
| `module_id` | string | 所属模块编号 |

## 7. 核验体系

### 7.1 核验标准

| 要求 | 说明 |
|------|------|
| **逐条比对** | 每一条条文必须与官方来源（全国人民代表大会公报 / 国务院公报 / flk.npc.gov.cn）逐字比对 |
| **多版本覆盖** | 若有修订，必须覆盖每一版本的条文，并标注版本链 |
| **具名签署** | 每一条条文在 `verifications.json` 中由核验人具名签署（"Vicky Wu (律师/税务师/专利代理师)"） |
| **不可由 LLM 代工** | LLM 生成的文本**不可**直接标注为 `verified`，必须经人类专家比对后方可变更状态 |
| **来源可追溯** | 每一条条文记录 `source_url` 和 `source_accessed_at`，任何用户可自行比对验证 |

### 7.2 核验工具链

复用并完善现有的 `verify_kb.py` 工具：

```bash
# 交互式逐条核验
python -S -m knowledge_base.verify_kb review
# 核验进度报告
python -S -m knowledge_base.verify_kb report
# 查看待核验条文
python -S -m knowledge_base.verify_kb pending
# 查看指定条文详情
python -S -m knowledge_base.verify_kb show <节点id>
```

### 7.3 构建流水线

```bash
# Step 1: 从 SEED（官方来源粘贴的条文）生成 statutes.jsonl
python -S -m knowledge_base.build_statute build
# Step 2: 运行完整性校验
python -S -m knowledge_base.build_statute validate
# Step 3: 专家核验（交互式，必须本人操作）
python -S -m knowledge_base.verify_kb review
# Step 4: 运行全量测试
python -S -m unittest discover -s tests -t . -p "test_*.py"
# Step 5: 打包发布
```

### 9.1 分层定价

| 层级 | 价格 | 包含内容 |
|------|------|----------|
| **免费层** | ¥0 | M1 民法典、M2 刑法、M3 公司法、M4 税法、M5 专利法（最常用 5 法）+ 失效法陷阱模块 |
| **专业版** | ¥5,000/年 | 免费层 + M6-M10（民事程序/行政/知产/劳动/刑事程序） |
| **企业版** | ¥20,000/年 | 专业版 + M11-M14（经济/建筑/金融/环境）+ API 接口 + 定期更新 + 邮件支持 |
| **定制版** | ¥50,000-¥100,000/年 | 企业版 + 定制法律模块（如行业监管法规、地方性法规）+ 专属 SL |

### 9.2 为什么免费层放最常用的 5 法
1. **降低试用门槛**：开发者可以直接下载最常用的法律模块，无需付费即可验证数据质量。
2. **建立信任**：免费模块是产品最好的广告。用户通过免费模块验证了"每一条都经过核验"的真实性后，更愿意为专业模块付费。
3. **网络效应**：免费模块带动更多人使用，社区贡献者可能参与核验或报告问题，提高产品整体质量。

### 9.3 收入预测（保守估计）

| 年份 | 免费用户 | 专业版用户 | 企业版用户 | 年收入 |
|------|----------|------------|------------|--------|
| 第 1 年 | 500 | 20 | 5 | ¥200,000 |
| 第 2 年 | 2,000 | 80 | 20 | ¥800,000 |
| 第 3 年 | 5,000 | 200 | 50 | ¥2,000,000 |

> 以上为保守估计，假设转化率为 4%（免费→专业）和 1%（免费→企业），且品牌认知度和销售能力随产品成熟度逐年提升。

## 10. 技术架构

### 10.1 数据流

```
官方来源 (.doc / .pdf / 网页)
        │
        ▼
  粘贴进 SEED (人工 + textutil 辅助解析)
        │
        ▼
  build_statute.py 构建 statutes.jsonl
        │
        ▼
  validate 完整性校验
        │
        ▼
  verify_kb.py 专家逐条核验
        │
        ▼
  verifications.json 核验台账
        │
        ▼
  全量测试 (unittest, 110 用例)
        │
        ▼
  打包 → GitHub Release 发布
```

### 10.2 技术栈

| 组件 | 技术 | 说明 |
|------|------|------|
| 数据格式 | JSONL (statutes) + JSON (verifications) | 机器可读、易于 diff、Git 版本控制友好 |
| 构建工具 | Python 3 (stdlib only) | `build_statute.py`, `verify_kb.py`, 测试框架 |
| 解析工具 | macOS `textutil` (doc → txt) + Python 正则 | 从官方 .doc 文件提取条文 |
| 核验工具 | `verify_kb.py` (交互式 CLI) | 逐条比对、签署、进度跟踪 |
| 测试框架 | Python `unittest` | 110 用例，`python -S` 零依赖 |
| 版本控制 | Git + GitHub | 代码、数据、文档统一管理 |
| 分发 | GitHub Releases + GitHub Pages | 模块独立发布 |
| CI/CD | GitHub Actions | 自动化测试 + 构建验证 |

### 10.3 核验流水线自动化程度

| 步骤 | 自动化程度 | 说明 |
|------|------------|------|
| 官方来源获取 | 手动 | 下载 .doc 或从 flk.npc.gov.cn 复制 |
| 条文解析 | 半自动 | `textutil` 转 txt + Python 解析 + 人工校对 |
| 构建 statutes.jsonl | 全自动 | `build_statute.py` |
| 完整性校验 | 全自动 | `validate` 命令 + CI |
| 逐条核验 | 手动（专家） | `verify_kb.py` 提供交互式界面，但比对判断必须由人完成 |
| 测试 | 全自动 | `unittest discover` + CI |
| 打包发布 | 半自动 | Python 脚本生成模块包，手动上传 GitHub Release |

> **不可自动化的一步**：逐条核验。这是产品的核心价值所在——每一条都有真人专家的签字背书。如果这一步自动化了（比如用 AI 自动比对），产品就失去了"可信度"这一核心差异化优势。

## 12. 风险评估与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 核验工作量过大（全量 ~5,500 条） | 高 | 进度延迟 | 分模块推进，优先 MVP；未来可招募兼职法学生/律师助理辅助核验 |
| 官方 .doc 源文件获取困难 | 中 | 部分法律无法核验 | 多渠道获取（公报、官网、同行共享）；标注"源文件缺失，暂未核验" |
| 法律修订导致 KB 过时 | 中 | 数据时效性下降 | 版本轴设计天然支持修订跟踪；定期巡查重要法律的修订动态 |
| 免费模块被大规模滥用 | 低 | 付费转化率低 | 免费模块仅覆盖 5 法，专业领域需求（程序法、金融法等）仍须付费 |
| 竞品跟进（大厂推出类似产品） | 中 | 差异化优势削弱 | 专家签名+核验台账+版本轴 构成壁垒；开源社区生态是护城河 |
| 个人时间精力限制 | 高 | 进度缓慢 | 分模块推进，每完成一个模块即发布，不求全量同时上线 |

## 仓库对齐备注（由 AI 于 2026-08-07 添加，待用户修订）
- **脚本路径**：仓库内为 `knowledge_base/verify_kb.py` 与 `knowledge_base/build_statute.py`，运行方式为 `python -S -m knowledge_base.verify_kb ...` / `python -S -m knowledge_base.build_statute ...`（非规格书正文里的 `knowledge_base.verify_kb` 包导入写法）。
- **当前节点数（与正文 5.1 表略有出入）**：民法典 27（正文写 26）、公司法 16（正文写 15）、专利法 30（一致）；企业所得税法 60 / 个人所得税法 22 按条数看**已是全文覆盖**。
- **信任分级**：本规格书默认"全部 verified"。实际落地采用两级——`Tier A 专家核验`（现有 212，继续作 Bench 评测 ground truth）+ `Tier B 官方全文提取`（从官方 .doc 逐字提取、未逐条签核，先以 Tier B 发布全集包，再逐步升 A）。详见项目 MEMORY.md「产品方向转折」段。
- **失效法模块**：已对应 Bench 的 `DEPRECATED_LAW_NAMES` 机制（单真相源，KB 不存旧法节点）。
- **全集包落地形态**：以 `packs/{law_code}_full.jsonl`（+ 派生 `.md`/`.csv`）独立存放，不污染 Bench 的 212 节点 `statutes.jsonl` 及其覆盖测试。
